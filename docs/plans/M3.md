## 1. Context

M2 is complete and merged (`main` at `d83c5bb`, PR #20). The final M2 verification on 2026-11-04 passed: lint, typecheck, 215 tests and build green; CI green on `main`; all Section 8 browser checks passed.

M3's milestone row (brief §5) says *"Team CRUD, persistence, analysis, export and import; validation shared between form and import; corrupted storage recovers."* As with M2, M3 means the **full detailed spec** in the brief:

- **§2 Teams**
  - create, rename and delete named teams
  - at most 6 Pokémon per team, each species at most once
  - add a Pokémon from the list or the detail page; remove it; reorder the team
  - an optional nickname per member: *"1 to 12 characters, letters, numbers and spaces only"*
  - teams persist across reloads, in the browser
  - export a team to a JSON file, and import one back
- **§2 Team analysis**
  - per attacking type, how many members are weak to it, resist it, or are immune to it
  - highlight any type that 3 or more members are weak to *"and none resist"*
  - the team's average for each base stat
- **§3.1**
  - team list and team detail routes
  - user state kept separate from API data, *justified in writing*
  - loading, empty and error (with retry) on views that fetch
  - *"Form validation (team names, nicknames) gives clear, inline messages, and the same rules are applied to imported files"*
  - keyboard-usable, labelled controls; works from 360px
- **§3.5**
  - browser storage and imported files are untrusted and validated before use
  - imported files are size-limited, schema-validated, and checked with the same rules as the form
  - a hostile file must not crash the app, corrupt existing teams or inject markup: *"Prove it with tests"*
  - storage carries a schema version; corrupted or outdated storage is detected on load, and the user can recover instead of getting a white screen
- **§3.7**
  - unit tests on team rules, nickname validation, storage migration and import validation
  - component tests for every view that fetches

## 3. Decisions (approved 2026-11-04)

The reasoning for each is logged in `docs/DECISIONS.md`. Numbering continues from M2 (D1–D7).

| # | Decision | Choice |
|---|---|---|
| D8 | Team state | **React Context + `useReducer`** in a `TeamsProvider`. The reducer calls pure domain functions; a plain storage module loads and saves. No state library. API data stays in TanStack Query and list UI state stays in the URL. |
| D9 | Persistence | **`localStorage`.** If storage is blocked (`SecurityError`), teams work in memory with a visible "won't be saved" notice. If a save fails (`QuotaExceededError`), the state is kept in memory and a notice suggests exporting. |
| D10 | Team representation | `Team = { id, name, members: { species, nickname }[] }`. Members are stored as **species name + optional nickname** only; types, stats and artwork always come from PokéAPI. Array order is team order. No nickname = `null`. **Team ids from `crypto.randomUUID()`** behind one `newTeamId()` helper. Ids read from the URL or storage are validated as UUID-shaped. |
| D11 | Team names | Required. **Trimmed** before storing. 1–30 characters (code points), no control characters, other characters allowed (React renders them as text). **Must be unique**: names are compared after trimming, NFC normalisation and lower-casing, so "Rain Team", "rain team" and " Rain Team " clash. Renaming a team to a different capitalisation of its own name is allowed. The same rule applies to create, rename, import and stored data. |
| D12 | Nicknames | Optional. **Unicode letters, numbers and spaces only** (`/^[\p{L}\p{N} ]+$/u` after NFC normalisation), **1–12 characters** counted as code points. No punctuation or symbols. Ends are trimmed. Only the normal space (U+0020) counts as a space. Empty or spaces-only input means no nickname. |
| D13 | Shared validation | **zod schemas in the domain layer**, used by the forms, the storage loader and the import parser. Messages are written once (zod 4 `error` param). No form library. |
| D14 | Storage version and recovery | Envelope `{ version, teams }`, a migration runner, and **salvage** of valid teams. **Stored data that couldn't be fully read is never overwritten until the user explicitly chooses** to keep the valid teams or to start over. A download of the original data is offered first. Data from a **newer version** is never touched automatically. |
| D15 | Team analysis | Weak = 2×/4×, resist = ½×/¼×, immune = 0×, shown as **3 separate counts**. A type is **highlighted when ≥ 3 members are weak and no member resists *or* is immune** (immunity counts as protection). Average of each base stat. |
| D16 | Reordering | **Move up / Move down buttons**, keyboard-accessible, no drag-and-drop. |
| D17 | Two open tabs | **Sync with the `storage` event.** A tab reloads and re-validates teams when another tab saves. Limitation documented: no merging of simultaneous edits (see §4.3). |
| D18 | Deleting a team | **Requires confirmation** (inline, 2-step). |

No new dependencies.

## 4. Technical specifications

These are implementation specs, not decisions to log.

### 4.1 Storage format (D9, D10, D14)
- Key: `dexter.teams`. Value: JSON `{ "version": 1, "teams": Team[] }`.
- **Load outcomes**

  | What is stored | Outcome | Teams shown | Saving |
  |---|---|---|---|
  | Nothing | `empty` | none | normal |
  | Valid envelope, all teams valid | `ok` | all | normal |
  | Older version **with** a migration | migrate, validate, then treat as `ok` or `salvaged` | — | — |
  | Valid envelope, some teams invalid (bad rules, duplicate id, or a duplicate name: the first one is kept) | `salvaged` | the valid ones, in memory | **paused** |
  | Invalid JSON, wrong shape, or an older version **without** a migration | `unreadable` | none | **paused** |
  | Version higher than the app knows | `newer-version` | none | **paused** |
  | `localStorage` throws on access | `unavailable` | in memory | not possible |

- **While saving is paused**, actions that change teams are disabled. A banner explains why, so nothing typed in that state can be lost.
  - **Salvaged:** the banner offers *Download original data* and *Keep the valid teams* (this saves the cleaned teams, replacing the original).
  - **Unreadable / newer version:** the banner offers *Download saved data* and *Start with no teams* (with confirmation; this replaces the original).
- **Saving after each change:** `saveTeams` never throws. A `QuotaExceededError` sets the status to `save-failed`, keeps the state in memory, and shows a notice that suggests exporting.

### 4.2 Team file format and import rules (export/import)
- **File:**
  ```json
  { "format": "dexter-team", "version": 1,
    "team": { "name": "Rain team", "members": [ { "species": "pikachu", "nickname": "Sparky" } ] } }
  ```
  - One team per file.
  - The team `id` is **not** exported.
  - Name: `dexter-team-<slug>.json`, 2-space indented.
  - Created with Blob → `URL.createObjectURL` → `<a download>` → `URL.revokeObjectURL`.
- **Import checks, in order.** Any failure lists every problem as plain text in `role="alert"`, and nothing changes.
  1. File size ≤ **16 KB** (`File.size`, checked **before** reading; the largest valid file is under 2 KB).
  2. Valid JSON.
  3. `format` is `"dexter-team"` and `version` is known.
  4. The same zod rules as the forms: team name (D11), ≤ 6 members, unique species, nicknames (D12).
  5. Every species is in the **species index** (so `pikachuu` and `pikachu-gmax` are rejected, consistent with D7).
  6. **The team name doesn't clash with an existing team** (D11 comparison). Message: *"A team called 'Rain team' already exists. Rename or delete that team, then import again."*
- **Success:** a **new** team with a new id is added. Existing teams are never replaced or changed.

### 4.3 Two tabs (D17)
- Each tab listens for `storage` events on `dexter.teams`. The event fires only in the *other* same-origin tabs ✓.
- On a change, the tab re-runs the normal load (same validation and outcomes as §4.1) and replaces its in-memory teams.
- **Limitation (documented in the README in T11):** this is "last save wins", with no merging. If 2 tabs change teams at nearly the same moment, the later save replaces the earlier one. A half-typed form (for example a nickname) in one tab isn't cleared by a sync, but when submitted it applies to the synced teams. If the team was deleted in the other tab, the submit gets a "team not found" message.

### 4.4 Adding to a team from the list and detail pages (UI)
- **Recommended interface** (from the brief's functional requirement; clear, accessible, fits 360px):
  - **one** "Add Pokémon to:" team selector, a native `<select>` labelled with the team names and their member counts ("Rain team (4/6)"), above the list grid and on the detail page
  - **one button per card**, "Add to *Rain team*", placed beside the card link rather than inside it, plus the same button on the detail page
- **Why:** a selector on every card (20 per page) is heavy at 360px. A pop-up menu per card needs the ARIA menu pattern and focus management.
- **Selected team:** in-memory UI state in `TeamsProvider`, not persisted.
- **Feedback:** in a `role="status"` live region. "Team is full" and "already in this team" use the T1 messages.
- **Edge cases:** no teams → a link "Create a team first"; storage paused (§4.1) → adding disabled, with the reason.

### 4.5 Analysis (D15)
- `analyzeTeam` is a pure function in `src/domain/` that reuses `getMatchups` (D5 rules: current damage relations, abilities ignored). For each of the 18 types it returns `{ weak, resist, immune, highlighted }`, with `highlighted = weak >= 3 && resist === 0 && immune === 0`.
- Averages: the mean of each base stat over the members, shown to 1 decimal.
- An empty team has no analysis; it shows an empty state instead.
- The analysis appears once every member's data has loaded. A failure shows error + retry inside the section.

## 6. Browser, storage and library facts the plan relies on

**Verified 2026-11-04:**
- **localStorage** (MDN `Window.localStorage`)
  - *"saved across browser sessions"*; keys and values are UTF-16 strings
  - private-window data is *"cleared when the last 'private' tab is closed"*
  - throws `SecurityError` if *"the request violates a policy decision"* (e.g. persistence blocked; blocking cookies probably counts)
- **Quota** (MDN *Storage quotas and eviction criteria*)
  - *"Browsers can store up to 5 MiB of local storage … per origin"*
  - *"Once this limit is reached, browsers throw a `QuotaExceededError`"*
  - data lasts until the user deletes it in browser settings; Safari *"proactively evicts"* script-created data for origins with no user interaction in 7 days
- **`storage` event** (MDN): *"not fired on the window that made the change"*. For localStorage it fires in other same-origin tabs.
- **`crypto.randomUUID()`** (MDN): *"available only in secure contexts"*; Baseline widely available since March 2022; returns a 36-character v4 UUID.
- **Secure contexts** (MDN): `https`, `127.0.0.0/8`, `::1`, `localhost` and `*.localhost` are potentially trustworthy. Plain `http://` on other hosts is not.
- **`URL.createObjectURL`** (MDN): Baseline since July 2015. *"To release an object URL, call `revokeObjectURL()`"*.
- **`useSyncExternalStore`** (react.dev): React prefers `useState`/`useReducer` when possible. This is part of D8's reasoning.
- **zod 4**: custom messages go in the `error` param. Installed `api.d.ts`: `message` is *"@deprecated … Use `error` instead"*.
- **jsdom 29.1.1** (inspected): `localStorage` and `Blob.text()` present; `URL.createObjectURL` absent.

**To check in the named step (not verified yet):**
- zod's handling of `__proto__` / `constructor` keys (T10 test).
- Whether `crypto.randomUUID` exists in the Vitest jsdom environment (T1; otherwise inject the id).
- `StorageEvent` fields `key` and `newValue` (MDN `StorageEvent`, T3).
- `File.size` / `File.text()` (MDN, T10).

**Assumptions:**
- **B1.** A file holds one team (the brief's wording).
- **B2.** Species names stay stable in PokéAPI. If one disappeared, the member would show "not found" with Remove (T6).
- **B3.** Teams stay small, so Context re-renders and synchronous writes are negligible.

### T5: Storage problems: recovery and notices (`feat/team-storage-recovery`)
- **Purpose:** §3.5 *"the user gets a way to recover rather than a white screen"*, following D14 and §4.1.
- **Scope** (Teams pages; the list and detail pages keep working):
  - **`salvaged`:** "*N* saved teams couldn't be read. Your other teams are shown, but changes aren't saved until you choose." Then **Download original data** and **Keep the valid teams**.
  - **`unreadable`:** "Your saved teams couldn't be read." Then **Download saved data** and **Start with no teams** (confirmation).

## 11. Open questions, risks and assumptions

- **Settled 2026-11-04:**
  - The §3.4 persistence documentation is written in **M3 T11**.
