## 4. Words used in this plan

- **Image digest:** the fingerprint (`sha256:…`) of one exact image. Tags like `main` can move; a digest can't.
- **Registry (GHCR):** GitHub's storage for Docker images, `ghcr.io/jenine-vertexpm/dexter`.
- **Blueprint / `render.yaml`:** a file describing Render services. Render reads it and creates or updates the service to match ("sync").
- **Deploy hook:** a secret URL; calling it tells Render "deploy now", optionally with a specific image (`imgURL`).
- **Runtime config:** settings read when the container starts, not baked in when the image is built.
- **envsubst / template:** nginx's start-up step that copies a `*.template` file, replacing `${NAME}` with the environment variable's value.
- **GitHub Environment:** a named target (`production`) in repo settings, with its own secrets and a rule that only `main` may use them.
- **Cold start:** the first request after a sleeping free service wakes it, taking about a minute.

## 6. Technical specifications

### 6.1 Validation rules (in `05-dexter-config.envsh`, POSIX sh, run by `set -e` entrypoint)
- `DEXTER_API_BASE_URL`: `^https://[a-z0-9.-]+(:[0-9]{1,5})?(/[A-Za-z0-9._~/-]*)?$`, no trailing slash. HTTPS only.
- `DEXTER_ENVIRONMENT`: `^[a-z][a-z0-9-]{0,19}$`.
- Missing or invalid → a clear message on stderr and `exit 1` → the container stops. On Render the new deploy never becomes healthy, so **the previous deploy keeps serving**.
- These character sets can't break out of a JS string, an nginx config line or a CSP header, so the generated `config.js` can't carry injected code. The app validates it again with zod (defence in depth, as for every other input, SECURITY.md).
- `DEXTER_API_ORIGIN` = scheme + host (+ port), derived, exported for envsubst. `NGINX_ENVSUBST_FILTER=^DEXTER_` (set in the Dockerfile; a fixed image setting, not config).

### 6.2 nginx files
- `nginx.conf` → `nginx/default.conf.template` (rendered to `conf.d/default.conf`). New block: `location = /config.js` → `default_type application/javascript; return 200 'window.__DEXTER_CONFIG__={"apiBaseUrl":"${DEXTER_API_BASE_URL}","environment":"${DEXTER_ENVIRONMENT}"};'`, plus `Cache-Control: no-cache` and the security-header include.
- `nginx/security-headers.conf` → `nginx/security-headers.inc.template` (rendered to `conf.d/security-headers.inc`; not `.conf`, so nginx doesn't auto-load it). `connect-src ${DEXTER_API_ORIGIN}`. Everything else byte-for-byte the same.
- `img-src` is **not** configurable: artwork URLs come from the API data and point at GitHub. That's recorded in the SECURITY.md note.

### 6.3 `render.yaml` (shape; exact keys verified in R7 against the Blueprint spec)
```yaml
services:
  - type: web
    name: dexter
    runtime: image
    plan: free
    region: frankfurt
    image:
      url: ghcr.io/jenine-vertexpm/dexter:main
    healthCheckPath: /healthz
    envVars:
      - key: DEXTER_ENVIRONMENT
        value: production
      - key: DEXTER_API_BASE_URL
        value: https://pokeapi.co/api/v2
```
- Port: Render detects 8080 or reads `PORT`. Verified in R7.
- Why `:main` in the file but a digest in CI: the file gives the service a starting image. Each CI deploy overrides it with the exact digest via `imgURL`, *"for that deploy only"* (Render deploy-hook docs). A manual sync redeploys `:main`, which is always the latest image pushed from `main`, so the two can't drift onto an older image.

### 6.4 Pipeline shape (`ci.yml`)
```
PR:          lint-and-typecheck ─┐
             image-and-e2e ──────┘  (required checks; unchanged contract)
push main:   lint-and-typecheck ─┐
             image-and-e2e ──────┴─► publish (packages: write) ─► deploy (environment: production,
                 └ uploads dexter-image.tar                        concurrency: production)
```
- `publish` and `deploy` have `if: github.event_name == 'push' && github.ref == 'refs/heads/main'`. Job-level permissions: the workflow stays `contents: read`; only `publish` gets `packages: write`.
- `deploy`: hook → poll `/version.txt` → `npm ci` → `npx playwright test e2e/headers.spec.ts e2e/runtime-config.spec.ts` with `E2E_BASE_URL=${{ vars.PRODUCTION_URL }}`.

## 11. Risks, open points, assumptions

- **Biggest risk: R1 says no** (Free can't run a prebuilt image). Then no R0 option meets "deploy the same image". The fallback options and their costs come back to you; nothing past R6 is wasted. *R1 (2026-11-10): the form allowed it; see below for what's still open.*
- **Gaps left open by R1, accepted by you on 2026-11-10.** Each is first tested in R7, and a "no" stops us there and comes back to you:
  - **No deploy hook on Free** → R8 can't deploy by digest the way the plan says. Alternatives would have to be weighed against the zero-cost rule, and a Render API key is a second secret.
  - **The image doesn't run on Free as expected** (port, health check, start-up) → fixed in R7 before anything else.
  - **Render changes a header** that `headers.spec.ts` checks exactly (HSTS, `Server`) → decided in R7/R8, never by weakening a header (see below).
  - **Billing page** → checked in R7 as part of the plan's existing step ("Check Billing still shows no payment method"). If a payment method is ever shown or required, stop.
- **Render changes its free tier again** (it cut bandwidth 20× this year). Mitigation: the image is platform-neutral (runtime config via env vars), so moving hosts means a new IaC file and a new deploy step only.
- **Suspension** if 5 GB is exceeded: the site goes offline until the 1st. Unlikely at this scale; documented.
- **Render's proxy alters a header** `headers.spec.ts` checks exactly (e.g. HSTS). R1 finds out; if so, we decide whether the test or the config changes, and never weaken a header just to pass.
- **Assumption:** a reviewer accepts Blueprints as the "documented equivalent" of Terraform. The D30 entry makes the case with the cited sources.
- **Out of scope** (brief §8 / not asked): staging or preview environments, custom domain, CDN, uptime monitoring, automatic rollback.
